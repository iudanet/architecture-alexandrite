# Выбор и настройка мониторинга в системе

## 1. Мотивация

Сейчас единственный источник данных - Яндекс Метрика на сайте онлайн-магазина.
Она показывает поведение посетителей, но не видит:

| Что не видно | Следствие |
|---|---|
| Заказы, поступающие через партнёрский API | Второй квартал компания принимает заказы от других продавцов, эта часть потока вне наблюдения |
| Состояние серверной части: MES API, CRM API, Shop API | Отказ или деградация обнаруживаются по жалобам |
| Длительность расчёта стоимости | Неизвестно, сколько заказов ждёт расчёта и как долго |
| Состояние очереди RabbitMQ | Неизвестно, копятся ли необработанные сообщения |
| Состояние баз данных и инстансов | Неизвестно, близка ли система к пределу |
| Прохождение заказа по статусам | Неизвестно, где заказы задерживаются и сколько их зависло |

О проблемах компания узнаёт от клиентов, а о серьёзности - из потерянных
контрактов. Производственные мощности при этом свободны и готовы к двукратному
росту, то есть потери вызваны не производством, а IT-ландшафтом.

Что даёт мониторинг:

| Результат | Как | Ценность для бизнеса |
|---|---|---|
| Обнаружение сбоя до жалобы | Оповещения по частоте ошибок и задержкам | Сохранение контрактов: сейчас они теряются, пока проблема не станет системной |
| Ответ на вопрос, выдержит ли система рост | Метрики использования ресурсов и пропускной способности | Планирование мощностей вместо реакции на отказ |
| Измерение узкого места | Задержки по сервисам и операциям | Ресурсы разработки идут на то, что действительно тормозит, а не на догадки |
| Контроль срока заказа | Метрики времени между статусами | Обещание "три недели" становится проверяемым |
| Оценка эффекта изменений | Сравнение метрик до и после | Видно, дал ли кеш или асинхронный расчёт результат |

Аргумент для бизнеса: компания уже потеряла несколько крупных контрактов и не
может назвать причину. Стоимость одного потерянного контракта выше стоимости
внедрения мониторинга.

## 2. Выбор подхода к мониторингу

Для разных частей системы применяются разные подходы.

| Часть системы | Подход | Обоснование |
|---|---|---|
| Shop API, CRM API, MES API, публичный API | RED (Rate, Errors, Duration) | Это сервисы, обрабатывающие запросы. RED отвечает на вопрос, как их видит потребитель: сколько запросов, сколько отказов, как долго |
| Инстансы EC2, базы данных, S3 | USE (Utilization, Saturation, Errors) | Это ресурсы. Важно, насколько они загружены и близки ли к пределу. RED к диску или процессору неприменим |
| RabbitMQ | USE плюс отдельные метрики очереди | Очередь одновременно ресурс (память, соединения) и канал доставки. Глубина очереди и возраст сообщения - показатели насыщенности |
| Фронтенды: Internet Shop, MES | Четыре золотых сигнала | Кроме частоты, ошибок и задержки важна насыщенность: время загрузки дашборда MES растёт при увеличении числа заказов |
| Расчёт стоимости в MES API | USE, не RED | RED применим к сервисам, управляемым запросами, и не подходит для пакетной и длительной обработки. Расчёт занимает 2-30 минут: значима не частота запросов, а насыщенность пула расчёта и длина очереди |
| Бизнес-процесс заказа | Отдельная группа метрик | Ни RED, ни USE не описывают прохождение заказа по статусам. Это метрики предметной области |

Основной подход - RED для сервисов и USE для ресурсов. Четыре золотых сигнала
применяются там, где нужна насыщенность в дополнение к RED.

## 3. Метрики

Ниже разобран предложенный список метрик: что берём, зачем и с какими ярлыками.
Далее отдельно перечислены метрики, добавленные сверх списка.

Общие ярлыки для всех метрик приложений: `service` (shop-api, crm-api, mes-api),
`environment` (dev, release, prod), `instance`, `version`. Ниже указаны только
дополнительные ярлыки, специфичные для метрики. Ярлыки `instance` и `job`
проставляются сборщиком автоматически.

Тип показателя выбирается по характеру величины (типы совпадают с моделью
Prometheus, которую поддерживает VictoriaMetrics):

| Тип | Применение в нашей системе |
|---|---|
| Счётчик | Только возрастающие величины: число запросов, ошибок, созданных заказов, сообщений в DLQ |
| Индикатор | Текущее значение: глубина очереди, число активных соединений, расчётов в работе, загрузка процессора |
| Гистограмма | Распределение: время ответа сервиса, длительность расчёта стоимости, время загрузки страницы. Позволяет считать перцентили |
| Сводка | Не применяется: перцентили считаются на стороне хранилища из гистограмм, что позволяет агрегировать по нескольким инстансам |

### 3.1. Очередь RabbitMQ

| Метрика из списка | Берём | Зачем | Ярлыки |
|---|---|---|---|
| Number of dead-letter-exchange letters in RabbitMQ | Да | Каждое сообщение в DLQ - потенциально потерянный заказ. Прямой ответ на жалобы "заказ не получен". Метрика первой важности | `queue`, `reason` (причина попадания: отказ обработчика, превышение попыток, истечение TTL) |
| Number of message in flight in RabbitMQ | Да | Показывает, успевает ли потребитель. Рост означает, что CRM API или MES API не справляются, заказы копятся перед обработкой | `queue`, `state` (ready - ожидают, unacked - взяты и не подтверждены) |

Разделение на `ready` и `unacked` обязательно: рост `ready` означает нехватку
пропускной способности потребителя, рост `unacked` - зависший обработчик, который
взял сообщение и не подтвердил. Это разные причины и разные действия.

### 3.2. Частота запросов (Rate в RED)

| Метрика из списка | Берём | Зачем | Ярлыки |
|---|---|---|---|
| Number of requests (RPS) for internet shop API | Да | Базовая линия нагрузки. Видно рост потока заказов и аномальные всплески | `route`, `method` |
| Number of requests (RPS) for CRM API | Да | То же для CRM. Дополнительно показывает, доходят ли до CRM события из очереди | `route`, `method` |
| Number of requests (RPS) for MES API | Да | Ключевая: MES API обслуживает и операторов, и партнёрский API. Ярлык канала показывает, кто создаёт нагрузку | `route`, `method`, `source` (ui, partner_api) |
| Number of requests (RPS) per user for shop API | Нет | Для B2C-магазина разбивка по конечному пользователю даёт кардинальность в десятки тысяч значений и не отвечает ни на один вопрос: аномалии по посетителям видит Яндекс Метрика |  |
| Number of requests (RPS) per user for CRM API | Нет | Продавцов немного, их индивидуальная нагрузка не влияет на систему |  |
| Number of requests (RPS) per user for MES API | Да, в измененном виде | Нужна не по пользователю, а по партнёру: партнёр может исчерпать ресурсы и вытеснить заказы B2C. Берём как `partner_api_requests_total` с ярлыком `partner_id` | `partner_id` |

Причина отказа от разбивки по пользователю: высокая кардинальность ярлыка резко
увеличивает объём хранения временных рядов. Для партнёров это оправдано - их
десятки, и от каждого зависит контракт. Для покупателей нет.

### 3.3. Задержка (Duration в RED)

| Метрика из списка | Берём | Зачем | Ярлыки |
|---|---|---|---|
| Response time (latency) for shop API | Да | Время оформления заказа влияет на конверсию | `route`, `method` |
| Response time (latency) for CRM API | Да | Отклик интерфейса продавца | `route`, `method` |
| Response time (latency) for MES API | Да | Прямая проверка жалобы операторов на медленный дашборд. Ярлык `route` покажет, тормозит именно список заказов | `route`, `method`, `source` |

Собираются как гистограммы, а не средние значения: среднее скрывает проблему.
Дашборд может открываться быстро у большинства и по 30 секунд у операторов с
большим числом заказов - это видно только по перцентилям p95 и p99.

### 3.4. Коды ответов (Errors в RED)

| Метрика из списка | Берём | Зачем | Ярлыки |
|---|---|---|---|
| Number of HTTP 500 for shop API, CRM API, MES API | Да | Отказы сервиса. Основа для оповещений о доле ошибок | `route`, `status_code` |
| Number of HTTP 200 for shop API, CRM API, MES API | Да, в измененном виде | Отдельный счётчик успехов не нужен: берётся один счётчик `http_requests_total` с ярлыком `status_code`, из него выводятся и 200, и 500, и 4xx | `route`, `method`, `status_code` |

Один счётчик с ярлыком `status_code` вместо трёх отдельных: так доля ошибок
считается делением без дополнительных метрик, и попадают все коды, включая 4xx.
Коды 4xx важны отдельно: для партнёрского API они означают неверную интеграцию на
стороне партнёра, а не дефект системы, и разбираются иначе.

### 3.5. Ресурсы приложений (Utilization в USE)

| Метрика из списка | Берём | Зачем | Ярлыки |
|---|---|---|---|
| CPU % for shop API, CRM API, MES API | Да | При одном инстансе на приложение загрузка процессора - предел масштаба. Для MES API особенно: расчёт стоимости зависит от числа полигонов и нагружает процессор | `instance` |
| Memory Utilisation for shop API, CRM API, MES API | Да | Исчерпание памяти ведёт к перезапуску и потере обрабатываемых заказов | `instance` |
| Kb transferred (received) for shop API | Да | Загрузка 3D-файлов создаёт основной входящий трафик, метрика показывает приближение к пределу канала | `instance` |
| Kb transferred (received) for CRM API, MES API | Да | Ниже приоритетом, но дешёвы в сборе: собираются тем же экспортером | `instance` |
| Kb provided (sent) for shop API, CRM API, MES API | Да | Исходящий трафик: выдача каталога и 3D-элементов конструктора | `instance` |
| Number of simultaneous sessions for shop API, CRM API, MES API | Да | Насыщенность по соединениям: показывает, сколько пользователей работает одновременно и близок ли предел пула обработчиков | `instance` |

Трафик и сессии - метрики второй очереди: они дополняют картину, но сами по себе
редко указывают на причину. Собираются, потому что не требуют отдельной работы:
входят в стандартный экспортер инстанса.

| Number of connections for MES db instance | Да | Дашборд MES выполняет тяжёлые запросы, соединения могут исчерпаться | `database` |

| Memory Utilisation for MES db instance | Да | То же для MES db | `database` |
| Size of shop db instance | Да | Рост объёма: планирование места и оценка, когда таблица заказов станет причиной медленных запросов | `database` |
| Size of MES db instance | Да | То же. Дополнительно: рост таблицы заказов напрямую связан с деградацией дашборда | `database` |

| `price_calculation_queue_depth` | Сколько заказов ждёт расчёта. Прямой показатель узкого места: один инстанс MES API считает последовательно | - |

### 3.8. Хранилище метрик

| Компонент | Технология | Назначение |
|---|---|---|
| Хранилище | VictoriaMetrics | Хранение временных рядов, совместимо с PromQL |
| Сбор | vmagent | Опрос конечных точек и приём метрик по push, буферизация при недоступности хранилища |
| Интерфейс | Grafana с базой конфигурации в PostgreSQL | Дашборды, общий интерфейс с логами и трейсами |
| Правила оповещений | vmalert | Вычисляет правила на метриках VictoriaMetrics и отправляет сработавшие оповещения в Alertmanager |
| Маршрутизация оповещений | Alertmanager | Группировка, подавление повторов, доставка по каналам: дежурный, поддержка, менеджер |

Почему VictoriaMetrics, а не Prometheus:

| Довод | Пояснение |
|---|---|
| Срок хранения | Prometheus рассчитан на оперативные данные, длительное хранение требует внешнего решения. Нам нужны 15 месяцев для сравнения год к году: ювелирные продажи сезонны, и без прошлогодних данных пик не отличить от аномалии |
| Кластеризация | Prometheus масштабируется вертикально и федерацией, что усложняет эксплуатацию. VictoriaMetrics разделяет приём, хранение и запросы, поэтому расширяется по мере роста нагрузки |
| Расход ресурсов | Меньше памяти и места на диске при том же наборе метрик. В компании один DevOps-инженер, экономия на обслуживании существенна |
| Оба режима сбора | vmagent совмещает опрос и приём по push. Для короткоживущих задач расчёта стоимости опрос не подходит: задача может завершиться между опросами |
| Совместимость | Поддерживается PromQL и формат метрик Prometheus, поэтому библиотеки инструментирования и готовые дашборды применимы без изменений |

Конфигурация Grafana размещается в управляемом PostgreSQL, а не во встроенной
SQLite: перенос дашбордов, прав и правил оповещений на другую СУБД позже
выполняется повторной настройкой, а не миграцией, и SQLite не допускает
нескольких экземпляров Grafana.

Модель сбора: основная - pull, push для задач, которые живут меньше интервала
опроса.

## 4. План действий

| № | Задача |
|---|---|
| 1 | Развернуть хранилище временных рядов VictoriaMetrics, срок хранения 15 месяцев для сравнения год к году |
| 1a | Развернуть vmagent как сборщик: опрос конечных точек сервисов по модели pull и приём метрик по push от короткоживущих задач |
| 2 | Развернуть Grafana с базой конфигурации в управляемом PostgreSQL, подключить к VictoriaMetrics, настроить вход через корпоративный провайдер |
| 3 | Подключить сбор метрик инфраструктуры: экспортер на каждый инстанс EC2 (процессор, память, диск, сеть) |
| 4 | Подключить метрики управляемых баз данных и S3 из Yandex Cloud |
| 5 | Подключить экспортер RabbitMQ: глубина очередей, неподтверждённые сообщения, DLQ |
| 6 | Инструментировать Shop API и CRM API: библиотека Micrometer, конечная точка `/metrics` для опроса, метрики RED |

Автоматическая реакция вместо ожидания оповещения:

| Показатель | Автоматическое действие |
|---|---|
| Частота запросов партнёра выше выделенной квоты | Backpressure: ограничение скорости, ответ с кодом 429 и указанием времени повтора. Заказы B2C не вытесняются |
| Глубина очереди на расчёт стоимости растёт | Backpressure: приём новых заявок на расчёт замедляется, приоритет отдаётся заказам B2C перед пакетными заявками партнёров |
| Отказы внешней системы превысили порог | Circuit Breaker: цепь размыкается, вызовы не выполняются, возвращается заглушка. Через интервал полуоткрытое состояние с пробным запросом |
| Загрузка процессора выше 90% | Добавление инстанса за балансировщиком |

Пороги для этих действий выводятся из тех же метрик, поэтому мониторинг является
предварительным условием: без измерений ограничения настраиваются наугад.

Уровни реакции:

| Уровень | Канал | Когда |
|---|---|---|
| Тикет в очередь работ | Трекер задач | Ресурс приближается к пределу, время на реакцию есть: диск 75%, процессор 70% |
| Оповещение дежурному | Мессенджер, рабочее время | Деградация без отказа: очередь растёт, задержки выше порога |
| Звонок дежурному | Автоматический вызов, круглосуточно | Отказ: сообщения в DLQ, недоступность БД или S3, доля ошибок выше 5% |
| Оповещение менеджеру | Мессенджер | Затронуты клиенты или партнёры: зависшие заказы, ошибки партнёрского API |
