# Архитектурное решение по трейсингу

## 1. Системы, которые покрываются трейсингом

Заказ проходит через три приложения и очередь. Места, где он может остановиться:

| Место | Что может сломаться |
|---|---|
| Internet Shop | Пользователь нажал "Сделать заказ", запрос не дошёл до Shop API |
| Shop API | Заказ создан в Shop DB, но сообщение в очередь не отправлено |
| 3d files storage | Файл не загружен или недоступен, расчёт невозможен |
| Messages Queue | Сообщение потеряно, не имеет получателя, обработано с ошибкой без повтора |
| MES API, расчёт стоимости | Расчёт длится 2-30 минут, зависает, падает без записи результата |
| MES API, назначение | Заказ не попал в список операторов, статус не сменился |
| MES db, Shop DB | Статус записан в одну базу и не записан в другую |
| CRM API | Сообщение из очереди получено, заказ в CRM не создан |
| MES | Дашборд не показывает заказ, оператор его не видит |
| Публичный API для партнёров | Таймаут на стороне партнёра, заказ создан или не создан - неизвестно |

Приоритет покрытия: MES API, Messages Queue, Shop API, CRM API. Это путь заказа
от оформления до производства. Фронтенды (Internet Shop, MES) подключаются
вторым этапом, чтобы связать действие пользователя с серверным трейсом.

### Данные в трейсинге

Контекст операции делится на статическую и динамическую часть:

| Часть контекста | Содержимое | Назначение |
|---|---|---|
| Статическая (resource) | `service.name`, `service.version`, `deployment.environment`, идентификатор инстанса | Прикрепляется к каждому спану, позволяет отбирать данные по сервису и окружению |
| Динамическая | Путь и метод запроса, идентификатор заказа, статус перехода | Меняется от вызова к вызову, описывает конкретную операцию |

Обязательные атрибуты спанов:

| Атрибут | Назначение |
|---|---|
| `trace_id`, `span_id`, `parent_span_id` | Связывание шагов в один путь. При повторной обработке сообщения из очереди создаётся новый `span_id` в том же трейсе: так видно число попыток |
| `order.id` | Поиск по номеру заказа |
| `order.status_from`, `order.status_to` | Переход статуса на этом шаге |
| `order.source` | Канал: онлайн-магазин или партнёрский API |
| `order.partner_id` | Идентификатор партнёра для заказов через API |
| `customer.id` | Владелец заказа, только идентификатор |
| `service.name`, `service.version`, `deployment.environment` | Где выполнялся шаг |
| `messaging.system`, `messaging.destination`, `messaging.message_id` | Прохождение через RabbitMQ |
| `db.system`, `db.operation` | Обращения к БД без текста запроса с данными |
| `price.calculation.duration_ms`, `model.polygons` | Длительность расчёта и сложность модели |
| `http.method`, `http.route`, `http.status_code` | Внешние вызовы |
| `error`, `exception.type`, `exception.message` | Причина отказа шага |

В трейсинг не попадают: 3D-файлы и их содержимое, персональные данные покупателя
кроме идентификатора, платёжные данные, тексты SQL-запросов с параметрами.

## 2. Мотивация

Заказы теряются, и команда не может ответить, где именно. Разбор идёт со слов
клиента: менеджер получает жалобу, разработчик вручную сверяет записи в трёх
системах и очереди. Производственные мощности при этом свободны, то есть проблема
в передаче заказа между сервисами, а не в производстве.

Трейсинг даёт ответ на вопрос "где заказ и что с ним произошло" за минуты вместо
часов и позволяет находить зависшие заказы до жалобы клиента.

Логи по отдельности на этот вопрос не отвечают: они показывают события внутри
одного сервиса, но не связывают их в цепочку между сервисами и очередью.
Трейсинг фиксирует последовательность и длительность вызовов с общим
идентификатором, поэтому путь заказа виден целиком. Данных при этом больше, чем
у логов (оценка в разделе 3.5), и объём ограничивается семплированием и сроком
хранения.

### Метрики, на которые влияет внедрение

| Метрика | Тип | Сейчас | Ожидание |
|---|---|---|---|
| Время локализации причины инцидента | Техническая | Часы, разбор вручную по трём системам | Минуты, поиск по номеру заказа |
| Доля заказов, доходящих до статуса `CLOSED` | Бизнес | Неизвестна | Измерима, отклонения видны |
| Число заказов, зависших дольше SLA | Бизнес | Обнаруживается по жалобам | Обнаруживается автоматически |
| Время прохождения заказа по статусам | Бизнес | Не измеряется | Измеряется, видно узкое место |
| Доля потерянных сообщений в очереди | Техническая | Неизвестна | Измерима по разрывам в трейсе |

## 3. Предлагаемое решение

### 3.1. Технологии

| Компонент | Технология | Обоснование |
|---|---|---|
| Инструментирование | OpenTelemetry SDK | Отраслевой стандарт: поддерживается фреймворками Java и C#, автоинструментирование Spring Boot и ASP.NET, не привязывает к вендору |
| Сбор и обработка | OpenTelemetry Collector | Централизованная точка: приёмники по gRPC и HTTP, обогащение, фильтрация, семплирование, маскирование, экспорт |
| Хранение и поиск | Jaeger | Открытое решение, поиск по атрибутам, интерфейс просмотра пути заказа |
| Хранилище спанов | ClickHouse | Колоночное сжатие: спаны однотипны и сжимаются в разы лучше, чем в документном хранилище. Запросы по `order.id` и по длительности выполняются на SQL. Есть управляемый сервис в Yandex Cloud. Подключается к Jaeger через интерфейс удалённого хранилища (gRPC), запись выполняет экспортёр коллектора |

Java-сервисы (Shop API, CRM API) подключаются через агент OpenTelemetry без
изменения кода, C#-сервис (MES API) через пакет OpenTelemetry для .NET.
Компания владеет исходным кодом MES, поэтому доработка возможна.

### 3.2. Что нужно доработать

| Доработка | Где |
|---|---|
| Распространение контекста в заголовках HTTP (`traceparent`) | Shop API, CRM API, MES API, публичный API |
| Распространение контекста в заголовках сообщений RabbitMQ | Shop API, CRM API, MES API. Без этого трейс обрывается на очереди, а именно там теряются заказы |
| Атрибут `order.id` на всех спанах, связанных с заказом | Все три сервиса |
| Спан на операцию расчёта стоимости с длительностью и числом полигонов | MES API |
| Спан на смену статуса заказа с указанием перехода | Все три сервиса |
| Отправка спанов фронтенда, связка с серверным трейсом | Internet Shop, MES |

### 3.4. Связь с логированием

Трейс показывает, на каком шаге заказ остановился, логи - что произошло на этом
шаге. Связь обеспечивает атрибут `trace_id` в каждой записи лога: Jaeger и
хранилище логов (Loki, см. Task4) доступны из одной Grafana, переход выполняется
без сопоставления по времени.

Хранилища разные и выбраны под характер данных: спаны однотипны и сжимаются
колоночно, поэтому ClickHouse; записи логов разнородны и им достаточно
индексирования по меткам, поэтому Loki с блоками в S3.

Порядок разбора инцидента:

| Шаг | Инструмент |
|---|---|
| Оповещение о нарушении SLA заказа | Метрики и правила алертинга (Task2) |
| Найти, на каком шаге заказ остановился | Трейс по `order.id` |
| Понять причину отказа на этом шаге | Логи по `trace_id` того же запроса |

### 3.5. Объём данных и срок хранения

Трейсинг - самый требовательный к ресурсам вид телеметрии. Один запрос на
оформление заказа проходит через фронтенд, Shop API, очередь, MES API, обращения
к БД и S3: это порядка 20 спанов. Каждый спан с атрибутами занимает около 1 КБ.

| Показатель | Оценка |
|---|---|
| Спанов на запрос | около 20 |
| Объём одного спана | около 1 КБ |
| Объём на запрос | около 20 КБ |
| При 100 запросах в секунду в пике (допущение из Task1) | около 2 МБ в секунду, 170 ГБ в сутки |
| При хранении 30 суток без семплирования | около 5 ТБ |

Хранить это целиком нельзя: расходы на диски и на вычисления при поиске
несоразмерны пользе. Отсюда два решения.

**Первое: срок хранения 5 суток вместо 30.** Трейсы нужны для разбора свежих
инцидентов: жалоба на заказ поступает в течение нескольких дней, дальше разбор
идёт по логам и метрикам, которые дешевле. Исключение - трейсы с ошибками и
нарушениями SLA: они хранятся 30 суток, их объём мал.

**Второе: семплирование.**

| Категория | Доля | Причина |
|---|---|---|
| Трейсы с ошибкой | 100% | Каждый отказ нужен для разбора |
| Трейсы со сменой статуса заказа | 100% | Путь заказа должен быть полным, иначе теряется смысл внедрения |
| Трейсы расчёта стоимости дольше 5 минут | 100% | Кандидаты на зависание |
| Трейсы заказов партнёров | 100% | Потеря заказа партнёра ведёт к потере контракта |
| Остальные запросы | 5% | Достаточно для оценки распределения задержек |

Решение принимается на коллекторе после завершения трейса (tail sampling): для
отбора по ошибке и длительности нужен полный трейс, на входе эти признаки
неизвестны.

С семплированием и сроком 5 суток расчётный объём падает примерно до 30-50 ГБ,
а с колоночным сжатием ClickHouse занимает на диске в несколько раз меньше.

**Что ещё снижает расход:**

| Мера | Эффект |
|---|---|
| Не создавать спаны на внутренние вызовы внутри одного сервиса | Основной источник лишних спанов: инструментировать только границы сервисов, обращения к БД, очереди и внешним системам |
| Ограничить число атрибутов и их длину | Атрибуты занимают больше самого спана. В коллекторе задаётся предел длины значения |
| Не писать в спаны то, что уже есть в логах | Спан фиксирует факт и длительность шага, подробности остаются в логах |
| Агрегированные метрики вместо трейсов для оценки задержек | Гистограммы из Task2 дают перцентили дешевле, чем выборка по трейсам |

### 3.6. Автоматический мониторинг прохождения заказа и алертинг

Диаграмма с алертингом, новые элементы зелёным:
[`diagrams/c2-tracing-alerting.drawio`](./diagrams/c2-tracing-alerting.drawio),
рендер [`diagrams/img/c2-tracing-alerting.png`](./diagrams/img/c2-tracing-alerting.png)

Компонент **Order SLA Monitor** периодически опрашивает Jaeger и находит заказы,
нарушившие ожидаемое время перехода между статусами.

Пороги по статусам:

| Переход | Порог | Действие при превышении |
|---|---|---|
| `SUBMITTED` -> `PRICE_CALCULATED` | 45 минут | Алерт дежурному: расчёт зависает |
| `PRICE_CALCULATED` -> `MANUFACTURING_APPROVED` | 24 часа | Алерт продавцу: заказ не подтверждён |
| `MANUFACTURING_APPROVED` -> `MANUFACTURING_STARTED` | 48 часов | Алерт менеджеру производства |
| `MANUFACTURING_STARTED` -> `MANUFACTURING_COMPLETED` | 21 день | Алерт менеджеру: нарушение обещанного срока |
| `SHIPPED` -> `CLOSED` | 14 дней | Алерт поддержке: нет подтверждения доставки |
| Трейс заказа обрывается без следующего спана | 30 минут | Алерт дежурному: заказ потерян между сервисами |

Оповещения маршрутизируются через Alertmanager, общий с метриками (Task2):
технические отказы дежурному инженеру, нарушения бизнес-сроков менеджеру и
продавцу. Для заказов партнёров
отдельный маршрут, так как их потеря ведёт к потере контракта.

## 4. Компромиссы

| Ситуация | Ограничение |
|---|---|
| Трейсинг не показывает причину, если сервис упал до создания спана | Разрыв трейса виден, но причина ищется в логах. Трейсинг отвечает на вопрос "где", логи на вопрос "почему" |
| Расчёт стоимости до 30 минут | Спан живёт всё это время, требуется увеличенный таймаут экспорта и промежуточные события внутри спана |
| Фронтенд-трейсинг зависит от блокировщиков в браузере | Часть спанов не дойдёт, серверная часть трейса остаётся полной |
| MES написан на C#, компетенция в команде у одного разработчика | Инструментирование MES API упирается в его доступность. Снижается автоинструментированием без правки бизнес-логики |
| Полный сбор трейсов дорог при линейном росте заказов | Решается семплированием, но редкие проблемы могут не попасть в выборку. Компенсируется правилом 100% для ошибок, смен статуса и заказов партнёров |
| Срок хранения 5 суток | Инцидент, о котором сообщили позже, разбирается по логам и метрикам без трейса. Компромисс осознанный: хранение всех трейсов 30 суток обошлось бы в терабайты |
| Трейсинг нагружает и сами приложения | Создание спанов и экспорт расходуют процессор и память сервиса. Снижается пакетной отправкой и ограничением числа атрибутов |
| Внешние системы: транспортная компания, платёжный провайдер | Контекст трейса не пробрасывается, границы видны как выход за периметр |
| Заказы, созданные до внедрения | Не имеют трейсов, разбираются старым способом |

## 5. Безопасность

| Мера | Реализация |
|---|---|
| Аутентификация в интерфейсе трейсинга | Вход через корпоративный провайдер (SSO), без локальных учётных записей |
| Авторизация | Роль "Поддержка" и "Разработка": просмотр трейсов. Роль "Администратор": настройка. Продавцы и операторы доступа не имеют |
| Сетевая изоляция | Jaeger и коллектор недоступны из интернета, только из внутренней сети и через VPN |
| Защита канала | Приём спанов по OTLP через TLS, коллектор принимает только от известных сервисов |
| Данные в спанах | Запрещены персональные данные кроме идентификаторов, платёжные данные, содержимое 3D-файлов, тексты запросов с параметрами |
| Маскирование | Правило на коллекторе: удаление атрибутов, попадающих под запрет, до записи в хранилище |
| Срок хранения | 5 суток для обычных трейсов, 30 суток для трейсов с ошибками и нарушениями SLA, затем автоматическое удаление по политике |
| Аудит доступа | Журналируются входы и поисковые запросы в интерфейсе трейсинга |
