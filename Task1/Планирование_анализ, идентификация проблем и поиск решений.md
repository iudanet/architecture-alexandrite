# Планирование: анализ, идентификация проблем и поиск решений

Анализ выполнен по описанию системы и диаграмме контейнеров C4.

## 1. Текущее состояние

| Контейнер | Технология | Назначение |
|---|---|---|
| Internet Shop | Vue, TypeScript, Three.js | Заказ, загрузка 3D-модели, 3D-редактор |
| Shop API | Spring Boot | Каталог, приём 3D-файла, заказ со стороны покупателя |
| CRM | Vue, TypeScript | Интерфейс продавца |
| CRM API | Spring Boot | Подтверждение производства, закрытие заказа |
| MES | React, TypeScript | Интерфейс оператора: список заказов, назначение |
| MES API | C# | Назначение заказов, расчёт стоимости, статусы производства |
| Messages Queue | RabbitMQ | Обмен сообщениями между CRM API и MES API |
| Shop DB | PostgreSQL | Данные покупателей и заказов |
| MES db | PostgreSQL | Заказы, назначения, статусы производства |
| 3d files storage | S3 | 3D-файлы для расчёта |

Окружения: dev, release, prod. Каждое приложение и каждая БД - один инстанс.
БД обслуживает и чтение, и запись. Деплой в release и prod - вручную.

Допущения о нагрузке, используемые в расчётах остальных заданий:

| Показатель | Значение | Источник |
|---|---|---|
| Прирост заказов | 100 заказов в месяц к предыдущему | Описание компании |
| Заказов в месяц | около 1000 | Оценка по текущему обороту и приросту |
| Запросов в секунду на все сервисы | около 100 в пике | Оценка: интерфейсы операторов и продавцов, партнёрский API, просмотр каталога. Запросов существенно больше числа заказов: один заказ создаёт десятки обращений, а каталог смотрят без оформления |
| Пиковая нагрузка | вдвое выше средней | Правило планирования мощностей |

## 2. Проблемные места

### 2.1. Наблюдаемость

| № | Проблема | Следствие |
|---|---|---|
| 1 | Нет сквозного трейсинга | Невозможно ответить, где находится заказ и на каком шаге он остановился. Разбор идёт со слов клиента |
| 2 | Нет централизованного логирования | Поддержка тратит на разбор инцидента часы, логи разрознены по трём приложениям |
| 3 | Нет мониторинга инфраструктуры и приложений | Яндекс Метрика видит только фронтенд онлайн-магазина, заказы через API вне её охвата |
| 4 | Нет алертинга | О проблеме узнают из жалоб клиентов и потерянных контрактов |
| 5 | Нет метрик бизнес-процесса | Неизвестно распределение времени по статусам заказа и число зависших заказов |

### 2.2. Обмен сообщениями и целостность заказа

| № | Проблема | Следствие |
|---|---|---|
| 6 | Сообщения теряются, механизм повторной доставки не описан | Заказ навсегда остаётся в промежуточном статусе, клиент не получает изделие |
| 7 | Нет очереди недоставленных сообщений (DLQ) | Сообщение с ошибкой обработки исчезает без следа |
| 8 | Обработка сообщений не идемпотентна | Повторная доставка создаёт дубль заказа или откатывает статус |
| 9 | Статус заказа хранится в двух базах: Shop DB и MES db | Расхождение состояний, нет единого источника истины по заказу |
| 10 | Нет контроля SLA по заказу | Заказ висит месяцами, никто не получает сигнала о нарушении срока |

### 2.3. Разделяемая база

| № | Проблема | Следствие |
|---|---|---|
| 11 | Shop DB используется одновременно Shop API и CRM API | Связанность по данным: изменение схемы одним сервисом ломает другой, конкуренция за соединения |
| 12 | Каждая БД - один инстанс на чтение и запись | Тяжёлые аналитические запросы MES конкурируют с транзакциями, точка отказа без резерва |

### 2.4. Производительность MES

| № | Проблема | Следствие |
|---|---|---|
| 13 | Дашборд MES долго загружается, фильтр и пагинация не помогли | Операторы не видят новые заказы, страдает их вознаграждение и скорость производства |
| 14 | Расчёт стоимости занимает 2-30 минут в синхронном сценарии | Пользователь API ждёт ответа или получает таймаут, заказ теряется |
| 15 | Нет кеширования списка заказов и результатов расчёта | Повторный расчёт одной и той же модели выполняется заново |
| 16 | Нет ограничения нагрузки на публичный API | Поток заказов от партнёров вытесняет заказы B2C, деградация общая |
| 17 | Нет защиты от каскадных отказов при недоступности внешних систем и соседних сервисов | Приложение продолжает вызывать неработающий сервис, расходуя соединения и потоки. Отказ одного компонента распространяется на остальные |

### 2.5. Масштабируемость

| № | Проблема | Следствие |
|---|---|---|
| 18 | По одному инстансу на приложение, горизонтального масштабирования нет | Рост на 100 заказов в месяц упирается в потолок, отказ инстанса останавливает поток |
| 19 | Расчёт стоимости не выделен в масштабируемый пул воркеров | Тяжёлые модели блокируют обработку остальных заказов |
| 20 | Нагрузочное тестирование не проводится | Пределы системы неизвестны, планирование мощностей вслепую |

### 2.6. Процессы разработки

| № | Проблема | Следствие |
|---|---|---|
| 21 | E2E-сценарии прогоняются вручную одним QA-инженером | Релиз задерживается на месяц и более, исправления не доходят до продакшна |
| 22 | Деплой в release и prod вручную | Человеческий фактор, невозможность быстрого отката |
| 23 | Нет автотестов регрессии | Каждый релиз проверяется заново целиком |

### 2.7. Организация и риски знаний

| № | Проблема | Следствие |
|---|---|---|
| 24 | MES на C#, в команде один разработчик C# | Единственная точка знаний, изменения в MES блокируются его доступностью |
| 25 | React знает частично один фронтендер | Интерфейс MES развивается медленно |
| 26 | Один DevOps-инженер на три окружения и всю инфраструктуру | Внедрение наблюдаемости и автоматизации ограничено его ресурсом |

## 4. Приоритизация

### 4.1. Ход рассуждений

Компания теряет контракты и клиентов из-за заказов, которые не доходят до
производства. При этом причина неизвестна: производственные мощности свободны и
готовы к двукратному росту, значит проблема в IT-ландшафте. Пока нет ответа на
вопрос "где остановился заказ", любое улучшение производительности - догадка.

Отсюда порядок:

1. Сначала наблюдаемость. Она не устраняет проблему, но делает её измеримой и
   показывает, какие из остальных инициатив дадут эффект.
2. Затем целостность заказа. Потерянное сообщение - прямая причина жалоб
   "заказ не получен". Это дефект надёжности, а не производительности.
3. Затем производительность. Дашборд MES и синхронный расчёт стоимости бьют по
   операторам и пользователям API, но не приводят к потере заказа.
4. Затем архитектурный долг: разделяемая база, масштабирование, автоматизация
   тестов и деплоя.

Организационные инициативы (I16-I18) идут параллельно: один разработчик C# на
MES - риск, который блокирует все работы по MES независимо от приоритета.

### 4.2. Целевая архитектура через полгода

| Аспект | Сейчас | Через полгода |
|---|---|---|
| Наблюдаемость | Яндекс Метрика на фронтенде | Трейсинг сквозной по заказу, централизованные логи, метрики и алертинг по SLA |
| Доставка сообщений | RabbitMQ без гарантий | Подтверждения, повторы, DLQ, идемпотентные обработчики |
| Статус заказа | Дублируется в двух базах | Единый источник истины, расхождения выявляются автоматически |
| Расчёт стоимости | Синхронно, 2-30 минут | Асинхронно, пул воркеров, результат по готовности, кеш по хешу модели |
| Дашборд MES | Прямой запрос в БД | Кеш, реплика для чтения |
| Инстансы | По одному на приложение | Горизонтальное масштабирование за балансировщиком |
| Защита от перегрузки | Отсутствует | Backpressure на входе, Circuit Breaker на вызовах внешних систем |
| Shop DB | Общая для Shop API и CRM API | Разделены границы владения данными |
| Тестирование | E2E вручную | Автотесты в конвейере, ручное тестирование только на новых сценариях |
| Деплой | release и prod вручную | Автоматический с возможностью отката |

Целевое состояние: заказ проходит путь от `INITIATED` до `CLOSED` без ручного
вмешательства, любое отклонение видно на дашборде и вызывает алерт до жалобы
клиента. Система выдерживает двукратный рост нагрузки за счёт горизонтального
масштабирования и асинхронного расчёта.

### 4.3. Три инициативы на ближайшие полгода

Если выбрать только три:

Логирование (I2) не входит в тройку как отдельная инициатива, но выполняется
вместе с трейсингом: структурные логи с идентификатором заказа и трейсом нужны,
чтобы после определения места отказа увидеть его причину. Порядок работ внутри
этой пары описан в Task4: логирование трёх сервисов настраивается первым, так как
не требует согласованных изменений в трёх сервисах одновременно, затем на те же
сервисы добавляется трейсинг.

**1. I1 - Сквозной трейсинг с correlation id заказа.**
Первым, потому что без него неизвестно, где теряются заказы. Жалобы клиентов и
пользователей API - об одном и том же симптоме, но причина может быть разной:
потерянное сообщение, зависший расчёт, необработанный статус. Трейсинг превращает
неизвестность в конкретный список мест. Он же даёт основу для контроля SLA: заказ,
который не сменил статус за N часов, становится видимым.

**2. I4 - Надёжная доставка сообщений: повторы, DLQ, идемпотентность.**
Вторым, потому что это устраняет саму причину, а не улучшает наблюдаемость.
Заказ создаётся в CRM по сообщению из очереди от MES: если сообщение потеряно,
заказа нет ни у кого, и восстановить его нечем. DLQ и повторы дают гарантию
доставки, идемпотентность защищает от дублей при повторе. Эффект прямой:
исчезает класс жалоб "заказ не получен".

**3. I7 - Асинхронный расчёт стоимости с пулом воркеров.**
Третьим, потому что расчёт до 30 минут в синхронном сценарии - причина таймаутов
у пользователей API и очереди на тяжёлых моделях. Один инстанс MES API считает
модели последовательно, поэтому поток заказов от партнёров блокирует и заказы
B2C. Асинхронный расчёт с масштабируемым пулом снимает потолок пропускной
способности, а компания как раз готовится к двукратному росту.

Что осознанно откладывается и почему:

| Инициатива | Причина отложить |
|---|---|
| I9 разделение Shop DB | Дорого и рискованно, при этом не влияет на текущие жалобы напрямую |
| I13 автотесты E2E | Ускоряет поставку, но не устраняет потерю заказов |
| I3 метрики | Нужны, но трейсинг отвечает на первый по остроте вопрос: где остановился заказ |
| I11 масштабирование инстансов | Без асинхронного расчёта даёт меньший эффект: узкое место в длительной операции |
