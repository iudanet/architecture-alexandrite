# Архитектурное решение по кешированию

## 1. Мотивация

Две жалобы указывают на одну область:

| Жалоба | Причина |
|---|---|
| Операторы: дашборд MES долго загружается, фильтр и пагинация не помогли | Каждое открытие страницы выполняет запрос в MES db. Пагинация уменьшила объём выдачи, но не число запросов и не стоимость сортировки по дате на растущей таблице |
| Партнёры и покупатели: заказ выполняется месяцами | Расчёт стоимости занимает 2-30 минут и выполняется заново для каждого заказа. Один инстанс MES API считает модели последовательно, очередь на расчёт растёт |

Дашборд открывается каждым оператором многократно за смену, при этом данные
меняются редко относительно частоты чтения: заказ переходит между статусами
за часы и дни, а список запрашивается каждые несколько минут. Это классический
профиль для кеширования: много чтений, мало записей.

Расчёт стоимости зависит только от содержимого 3D-модели и прейскуранта. Одна и
та же модель даёт один результат, но считается повторно при каждом заказе.
Партнёры при интеграции часто отправляют типовые модели.

### Что включаем в кеширование

| Объект | Обоснование |
|---|---|
| Список заказов для дашборда MES по статусам и страницам | Основной источник жалоб операторов, высокая частота чтения |
| Карточка отдельного заказа | Запрашивается при открытии заказа оператором и продавцом |
| Результат расчёта стоимости по хешу 3D-модели | Устраняет повторный расчёт длительностью до 30 минут |
| Справочники: прейскурант материалов, каталог готовых элементов конструктора | Меняются раз в недели, читаются при каждом расчёте и открытии магазина |
| Статические файлы онлайн-магазина и 3D-элементы конструктора | Снижают нагрузку на Shop API и трафик |

### Что не кешируем и почему

| Объект | Причина отказа |
|---|---|
| Платёжные операции и суммы к оплате | Недопустимо получить устаревшие данные: ошибка в расчёте ведёт к финансовым и юридическим последствиям |
| Персональные данные покупателя, данные авторизации | Секретная информация: кеш увеличивает поверхность атаки, а выигрыш незначителен |
| Запись смены статуса заказа | Операция изменения данных, а не чтения. Кеш здесь дал бы риск рассогласования при отказе |
| Содержимое 3D-файлов покупателей | Данные редко запрашиваются повторно: файл читается один раз при расчёте. Объём при этом велик, кеш вытеснял бы полезные данные |
| Список заказов конкретного покупателя в личном кабинете | Данные редко запрашиваются: покупатель заходит проверить статус один-два раза за срок изготовления. Кеш не окупится |

## 2. Предлагаемое решение

### 2.1. Клиентское или серверное

Применяются оба, для разных объектов.

| Объект | Тип | Обоснование |
|---|---|---|
| Статические файлы, 3D-элементы конструктора | Клиентское, заголовки `Cache-Control` и `ETag`, плюс CDN | Данные одинаковы для всех, не зависят от пользователя, меняются редко. Убирает и задержку сети, и передачу данных |
| Список заказов дашборда MES | Серверное | Список общий для операторов: клиентский кеш пришлось бы наполнять у каждого отдельно, эффект был бы меньше. Данные меняются: оператору важно видеть новые заказы, поэтому нужен контроль срока жизни на сервере |
| Карточка заказа | Серверное | То же: общий доступ, нужна инвалидация при смене статуса |
| Результат расчёта стоимости | Серверное | Результат нужен серверу для дальнейшей обработки заказа, а не браузеру |
| Справочники | Серверное | Используются серверной логикой расчёта |

Основное решение - серверное кеширование в Redis. Клиентское применяется как
дополнение для статики.

#### Заголовки клиентского кеширования

| Ресурс | Заголовок | Обоснование |
|---|---|---|
| Статические файлы приложения с хешем в имени | `Cache-Control: public, max-age=31536000, immutable` | Имя файла меняется при сборке, поэтому длительный срок безопасен |
| 3D-элементы конструктора | `Cache-Control: public, max-age=86400` плюс `ETag` | Меняются редко, при изменении браузер получит `304 Not Modified` по условному запросу |
| Каталог готовых изделий | `Cache-Control: public, max-age=300` | Каталог одинаков для всех посетителей, поэтому кешируется и на CDN. Цены и наличие меняются, пять минут допустимо |
| Список заказов, карточка заказа, личный кабинет | `Cache-Control: private, no-cache` | Ответ проверяется на актуальность перед использованием |
| Ответы партнёрского API | `Cache-Control: no-store` | Данные заказа не должны оставаться в промежуточных кешах |

Используется `max-age`, а не `Expires`: относительное время не требует
согласования часовых поясов. Директива `private` запрещает промежуточным кешам
хранить ответ конкретного пользователя. Для 3D-элементов включается `ETag`:
по условному запросу `If-None-Match` сервер отвечает `304 Not Modified` без
передачи файла, что снижает трафик на крупных моделях.

### 2.2. Паттерн серверного кеширования

Выбран **Cache-Aside** для заказов и результатов расчёта, **Refresh-Ahead** для справочников.

| Паттерн | Оценка для нашего случая |
|---|---|
| **Cache-Aside** | Выбран. Приложение само читает кеш и при промахе обращается к БД. Устойчив к отказу кеша: при недоступности Redis запросы идут в БД, скорость падает, доступность сохраняется. Позволяет держать в кеше модель, отличную от модели БД: список заказов для дашборда собирается запросом с соединением таблиц и кладётся под одним ключом. Профиль дашборда MES - много чтений, мало записей - соответствует паттерну |
| Read-Through | Не выбран. К базе обращается кеш, а не приложение, поэтому при ошибке кеша данные брать неоткуда и запрос завершится отказом. Для MES это недопустимо: операторы не смогут работать. Кроме того модель данных в кеше должна совпадать с моделью БД, а нам нужен собранный список заказов, а не построчная копия таблицы |
| Refresh-Ahead | Выбран частично, только для справочников. Упреждающее обновление до истечения срока даёт согласованность часто читаемых данных без промахов. Подходит прейскуранту и каталогу элементов: они меняются предсказуемо редко, а читаются при каждом расчёте. Для списка заказов не подходит: пришлось бы обновлять все комбинации статуса и страницы, большая часть которых не запрашивается |
| Write-Through | Не выбран. Запись идёт через кеш, и кеш становится обязательным звеном на пути записи. Смена статуса заказа - критичная операция: при недоступности Redis оператор не сможет взять заказ в работу. Плюс паттерна (кеш и БД всегда согласованы, инвалидация не нужна) не перевешивает этот риск. Дополнительно в кеш попадали бы данные, которые никто не читает: старые заказы |
| Write-Behind | Не выбран. База обновляется асинхронно после ответа клиенту. Для статуса заказа это означает окно, в котором подтверждение получено, а в БД записи нет. При отказе кеша до сброса в базу изменение теряется. Для заказа, от которого зависит производство и обещание срока клиенту, потеря недопустима |

Комбинация Read-Through и Write-Through, которую часто применяют при активных
чтении и записи, здесь не подходит по той же причине: оба паттерна ставят кеш
в критический путь.

#### Условия применения Refresh-Ahead

В чистом виде паттерн отдаёт пустой ответ, пока фоновое обновление не наполнило
кеш: приложение читает только кеш и к источнику не обращается. Для прейскуранта
это означало бы невозможность расчёта стоимости. Поэтому:

| Мера | Назначение |
|---|---|
| Прогрев при старте сервиса | Справочники загружаются в кеш до приёма запросов, первый запрос не получает пустой ответ |
| Запасной путь к источнику | Если ключ справочника пуст, выполняется чтение из БД как в Cache-Aside. Пустой ответ не возвращается |
| Интервал обновления меньше срока жизни ключа | Обновление каждые 6 часов при TTL 24 часа: даже при пропуске двух циклов данные остаются |
| Мониторинг фонового обновления | Отказ обновления не виден в запросах: без контроля кеш незаметно устареет. Метрика времени последнего успешного обновления и оповещение при превышении интервала |

### 2.3. Диаграмма последовательности

[`diagrams/seq-orders-cache.puml`](./diagrams/seq-orders-cache.puml),
рендер: [`diagrams/img/seq-orders-cache.png`](./diagrams/img/seq-orders-cache.png)

Диаграмма отражает три сценария: чтение списка заказов с попаданием и промахом,
запись смены статуса с инвалидацией, кеширование результата расчёта стоимости.

Участники: оператор, MES (React), MES API (C#), Redis, MES db (PostgreSQL),
RabbitMQ.

### 2.4. Структура ключей и срок жизни

| Ключ | Содержимое | TTL |
|---|---|---|
| `orders:status={status}:page={n}` | Страница списка заказов по статусу | 30 секунд |
| `order:{order_id}` | Карточка заказа | 5 минут |
| `price:{model_hash}` | Результат расчёта стоимости | 30 суток |
| `pricelist:current` | Прейскурант материалов | 24 часа, обновление по расписанию |
| `catalog:elements` | Элементы конструктора | 24 часа |

TTL списка заказов 30 секунд выбран как компромисс: операторам важно видеть новые
заказы (от этого зависит их вознаграждение), поэтому длинный срок недопустим.
При этом 30 секунд уже снимают основную часть повторных запросов, так как
дашборд обновляется чаще.

### 2.5. Стратегия инвалидации

Основная - **инвалидация на основе изменений**, дополнительная - **временная**,
для точечных случаев - **по ключу**.

| Способ | Оценка для нашего случая |
|---|---|
| **На основе изменений** | Основной. Кеш инвалидируется при смене статуса заказа: удаляются ключ карточки и ключи списков затронутых статусов. Данные согласованы сразу после записи, оператор видит актуальный список. Требует дисциплины: каждый путь записи должен инвалидировать кеш |
| **Временная (TTL)** | Дополнительный, как страховка. Даже если ключ не был удалён из-за пропущенной инвалидации, он устареет через 30 секунд. Сама по себе недостаточна: без инвалидации по изменению пришлось бы держать TTL в единицы секунд, что обесценивает кеш |
| **По ключу** | Применяется точечно. Ключ `order:{id}` удаляется адресно при изменении конкретного заказа, а не сбросом всех заказов. Минимизирует объём инвалидации |
| Основанная на запросах | Не подходит как основная. Инвалидация при каждом запросе на обновление данных обнуляла бы кеш дашборда при каждой смене статуса любого заказа. При текущем потоке заказов кеш не успевал бы наполняться |
| Программная | Не требуется. Условная инвалидация по проверке изменившегося значения нужна там, где событие изменения неявно, как в бронировании мест. У нас событие явное: смена статуса заказа, и его достаточно |

Порядок операций при записи: сначала транзакция в БД, затем инвалидация кеша.
Обратный порядок оставил бы устаревшие данные при откате транзакции.

При переходе заказа из статуса A в статус B удаляются ключи списков обоих
статусов: заказ исчез из одного списка и появился в другом.

Кеш расчёта стоимости по изменениям не инвалидируется: результат зависит от
содержимого модели, а оно неизменно. Инвалидация нужна только при изменении
прейскуранта, тогда удаляются все ключи `price:*`.

Справочники обновляются по расписанию упреждающим обновлением, инвалидация для
них не применяется.

## 3. Дополнительно: сравнение двух решений

Для дашборда MES возможны два варианта.

|  | Решение 1: Redis, Cache-Aside | Решение 2: Реплика для чтения |
|---|---|---|
| Описание | Список заказов кешируется в Redis с TTL 30 секунд, инвалидация по событию смены статуса. Диаграмма в разделе 2.3 | Для MES db создаётся реплика на чтение. Дашборд и отчёты читают с реплики, запись идёт в основной инстанс |
| Плюсы | Отклик в единицы миллисекунд. Снимает нагрузку с БД полностью для повторных запросов. Дешевле по ресурсам. Тот же кеш переиспользуется для расчёта стоимости и справочников | Не требует изменений логики приложения кроме строки подключения. Нет риска устаревших данных сверх задержки репликации. Снимает конкуренцию тяжёлых отчётных запросов с транзакциями |
| Минусы | Требует доработки MES API: чтение кеша, инвалидация во всех путях записи. Риск устаревших данных при пропущенной инвалидации | Не устраняет стоимость самого запроса: сортировка растущей таблицы выполняется каждый раз. Задержка репликации даёт устаревшие данные без контроля со стороны приложения. Дороже: ещё один инстанс БД |

**Заключение.** Для дашборда выбирается решение 1: жалоба операторов вызвана
частотой одинаковых запросов, и кеш устраняет её полностью, тогда как реплика
лишь переносит нагрузку. Решение 2 остаётся полезным независимо от кеша, но для
другой задачи: вынос аналитических и отчётных запросов, которые кешировать
бессмысленно из-за уникальности выборок. Оба решения не исключают друг друга,
но первым внедряется кеш как более дешёвый и точнее отвечающий проблеме.
