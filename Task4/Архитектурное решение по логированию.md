# Архитектурное решение по логированию

## 1. Что логируем

### 1.1. Системы

| Система | Что собираем | Приоритет |
|---|---|---|
| MES API | Расчёт стоимости, назначение заказа операторам, смены статусов производства, обработка сообщений из очереди | 1 |
| Shop API | Создание заказа, загрузка 3D-файла, отправка сообщений в очередь, вызовы партнёрского API | 1 |
| CRM API | Получение сообщений из очереди, подтверждение производства, закрытие заказа | 1 |
| Messages Queue | Отказы доставки, попадание сообщений в DLQ | 2 |
| MES | Ошибки интерфейса оператора, длительность загрузки дашборда | 3 |
| Internet Shop | Ошибки оформления заказа и работы 3D-редактора | 3 |

Приоритет 1: сервисы, через которые проходит заказ. Приоритет 2: очередь как
место потери сообщений. Приоритет 3: фронтенды, они дополняют картину.

### 1.2. Логи уровня INFO

| Событие | Поля |
|---|---|
| Заказ создан | время, `order_id`, `customer_id`, `source` (shop или partner), `partner_id`, сумма позиций |
| Загружен 3D-файл | время, `order_id`, `file_id`, размер, число полигонов |
| Смена статуса заказа | время, `order_id`, `status_from`, `status_to`, инициатор (система или пользователь), `user_id` |
| Запуск расчёта стоимости | время, `order_id`, `file_id`, число полигонов |
| Расчёт стоимости завершён | время, `order_id`, длительность, результат расчёта |
| Сообщение отправлено в очередь | время, `order_id`, `message_id`, топик |
| Сообщение получено из очереди | время, `order_id`, `message_id`, топик, число попыток |
| Заказ назначен оператору | время, `order_id`, `operator_id` |
| Заказ подтверждён к производству | время, `order_id`, `seller_id` |
| Заказ закрыт | время, `order_id`, причина закрытия: автоматически или вручную |
| Вызов партнёрского API | время, `partner_id`, метод, код ответа, длительность |

Обязательные поля каждой записи: `timestamp`, `level`, `service`, `version`,
`environment`, `trace_id`, `span_id`, `order_id` там, где событие связано с заказом.
Формат JSON: он разбирается сборщиком без правил парсинга.

### 1.3. Остальные уровни

| Уровень | Когда используется |
|---|---|
| FATAL | Отказ сервиса целиком: не удалось подключиться к БД при старте, исчерпана память, сервис завершает работу. Требует немедленной реакции дежурного |
| ERROR | Ошибочное состояние отдельной операции: расчёт стоимости упал, сообщение не обработано после всех попыток, запись в БД не удалась, недоступен S3. Сервис продолжает работать |
| WARN | Операция выполнена, но с отклонением: повторная попытка обработки сообщения, расчёт дольше 10 минут, ответ партнёрского API дольше 5 секунд, приближение к лимиту соединений БД |
| DEBUG | Отключён в продакшне. Включается точечно на время разбора инцидента через изменение уровня без перезапуска |
| TRACE | Только в dev-окружении, для отладки конкретного сценария |

DEBUG в продакшне не включается постоянно: при линейном росте заказов объём
логов вырастет непропорционально пользе.

## 2. Мотивация

Разбор ошибок идёт со слов клиента. Чтобы понять, что произошло на стороне
сервиса, разработчик и поддержка вручную сверяют состояния в трёх приложениях и
очереди. Это занимает часы на один инцидент, а число жалоб растёт вместе с
нагрузкой.

Централизованное логирование даёт: поиск по номеру заказа в одном месте,
воспроизведение цепочки событий, выявление повторяющихся отказов, обнаружение
аномалий до обращения клиента.

### Метрики, на которые влияет внедрение

| Метрика | Тип | Сейчас | Ожидание |
|---|---|---|---|
| Время разбора одного обращения | Техническая | Часы | Минуты, поиск по `order_id` |
| Доля обращений, закрытых поддержкой без привлечения разработки | Бизнес | Низкая, нет данных для разбора | Растёт: поддержка видит причину сама |
| Число повторяющихся отказов, дошедших до продакшна | Техническая | Неизвестно | Измеримо, видны частые ошибки |
| Время обнаружения инцидента | Техническая | По жалобе клиента | По правилу на частоту ошибок |
| Доля заказов с ошибкой обработки | Бизнес | Неизвестна | Измерима по логам уровня ERROR |

### Очерёдность логирования и трейсинга

Команда не сможет внедрить всё сразу. Порядок:

1. **Логирование MES API, Shop API, CRM API.** Логи дешевле в подключении:
   стандартные библиотеки, не требуют проброса контекста между сервисами.
   Дают немедленный эффект для поддержки.
2. **Трейсинг тех же трёх сервисов и очереди.** Отвечает на вопрос, где заказ
   остановился, чего логи по отдельности не показывают.
3. **Логирование очереди и фронтендов.**
4. **Трейсинг фронтендов.**

Логирование первым по порядку работ, потому что оно не требует согласованных
изменений в трёх сервисах одновременно и сразу снимает боль поддержки. Трейсинг
вторым: он даёт связность, но полезен только когда покрыт весь путь заказа.

По приоритету задач (Task1) первой инициативой идёт трейсинг: он отвечает на
вопрос, где теряются заказы, из-за которых компания теряет контракты.
Противоречия нет: критерии разные. Приоритет определяется влиянием на потери
бизнеса, порядок работ - трудоёмкостью и зависимостями. Логирование и трейсинг
внедряются одной инициативой на одних и тех же сервисах, логи настраиваются
раньше внутри неё.

## 3. Предлагаемое решение

### 3.1. Способы сбора

| Способ | Где применяется |
|---|---|
| Логирование приложений | Shop API и CRM API через Logback, MES API через Serilog: штатные средства фреймворков, вывод в поток вывода в формате JSON |
| Логирование с помощью агентов | Агент на каждом инстансе EC2 читает поток вывода приложения, парсит, маскирует и отправляет в хранилище |
| Системное логирование | Логи операционной системы инстансов и логи управляемых сервисов Yandex Cloud: БД, S3, RabbitMQ |
| Контейнерное логирование | Не применяется: приложения развёрнуты как EC2, а не в контейнерах. Понадобится при переходе на Kubernetes |

### 3.2. Технологии

| Компонент | Технология | Назначение |
|---|---|---|
| Формат логов | JSON, структурные логи | Разбор без регулярных выражений, поля доступны для фильтрации |
| Библиотеки | Logback с JSON-энкодером (Java), Serilog (C#) | Штатные средства платформ |
| Сбор | Grafana Alloy или Promtail | Агент на инстансе: чтение, разбор, маскирование, буферизация при недоступности хранилища |
| Хранение и поиск | Grafana Loki | Индексирование по меткам, сжатые блоки логов хранятся в S3 |
| Интерфейс | Grafana | Общий с метриками Task2 и трейсами Task3 |
| Правила оповещений | Grafana Alerting | Правила на частоту ошибок и аномалии, вывод в Alertmanager, общий с метриками |

### 3.5. Безопасность и чувствительные данные

| Мера | Реализация |
|---|---|
| Запрещено логировать | Персональные данные покупателя кроме `customer_id`, адрес доставки, платёжные данные, содержимое 3D-файлов, токены и пароли, тексты запросов с параметрами |
| Маскирование | Правила на агенте: поля с признаками персональных или платёжных данных заменяются на маску до отправки в хранилище |
| Контроль на этапе разработки | Проверка на запрещённые поля в конвейере сборки, ревью новых событий логирования |
| Доступ | Роль "Поддержка": поиск по логам приложений. Роль "Разработка": все логи своего сервиса. Роль "Администратор": настройка, метки, политики хранения. Продавцы и операторы доступа не имеют |
| Аутентификация | Через корпоративный провайдер (SSO), локальных учётных записей нет |
| Сеть | Хранилище и интерфейс недоступны из интернета, только внутренняя сеть и VPN |
| Передача | Логи передаются по TLS, агент аутентифицируется на хранилище |
| Аудит | Журналируются входы и поисковые запросы в интерфейсе |

### 3.6. Политика хранения

Логи разделяются метками потока: `service`, `environment`, `level`. Так поиск не
сканирует лишние данные, а права и срок хранения настраиваются на группу потоков.

| Категория | Срок хранения | Обоснование |
|---|---|---|
| ERROR, WARN продакшна | 90 суток | Разбор повторяющихся отказов и сезонных проблем |
| INFO продакшна | 30 суток | Достаточно для разбора обращений: жалобы поступают в пределах месяца |
| Логи заказов (события смены статуса) | 180 суток | Срок производства до трёх недель плюс претензионный период |
| dev и release | 7 суток | Нужны только на время работы над версией |
| DEBUG | 3 суток | Включается точечно, объём большой |

Оценка объёма: при 1000 заказов в месяц (допущение из Task1) и 15 событиях INFO на заказ это 15 тысяч
записей по 1 КБ, около 15 МБ в месяц по событиям заказа. С учётом технических
логов, запросов HTTP и роста нагрузки расчётный объём 5-10 ГБ в месяц на
продакшн. Блоки старше срока удаляются автоматически по политике хранения.
Свежие данные за 7 суток на быстрых дисках кеша Loki, остальное в S3: тот же тип
хранилища, что используется для 3D-файлов, отдельный бакет.

## 4. От сбора логов к анализу

### 4.1. Оповещения

| Правило | Порог | Действие |
|---|---|---|
| Частота ERROR в сервисе | Более 10 за 5 минут | Оповещение дежурному инженеру |
| Отказ расчёта стоимости | Более 3 за 10 минут | Оповещение дежурному: проблема в MES API или S3 |
| Сообщения в DLQ | Любое появление | Оповещение дежурному: заказы теряются |
| Ошибки партнёрского API | Более 5% ответов с кодом 5xx за 10 минут | Оповещение дежурному и менеджеру: риск потери контракта |
| Недоступность БД или S3 | Первое появление | Оповещение дежурному, приоритет высший |
| Отсутствие логов от сервиса | Нет записей 5 минут | Оповещение дежурному: сервис или агент не работает |

### 4.2. Поиск аномалий

Нужен: часть проблем не выражается через порог по ошибкам.

| Аномалия | Что означает | Реакция |
|---|---|---|
| Резкий рост числа создаваемых заказов: с единиц до тысяч за минуту | Атака или сбой интеграции партнёра, повторная отправка одних сообщений | Ограничение частоты запросов партнёра, оповещение дежурному |
| Падение числа заказов до нуля в рабочее время | Отказ оформления, который не даёт ошибок в логах | Оповещение дежурному |
| Рост доли повторных обработок сообщений | Обработчик не подтверждает сообщения, растёт риск дублей | Оповещение дежурному |
| Рост средней длительности расчёта стоимости | Деградация MES API или поток сложных моделей | Оповещение дежурному, оценка масштабирования |
| Один `order_id` в логах чаще ожидаемого | Цикл обработки, заказ обрабатывается повторно | Оповещение дежурному |

Базовый уровень: правила на отклонение от скользящего среднего за неделю по часам
суток. Этого достаточно, сезонность в продажах ювелирных изделий заметная.
Машинное обучение на этом этапе не нужно: нет истории для обучения.

## 5. Критерии выбора технологии

| Критерий | Grafana Loki | ClickHouse | VictoriaLogs | ELK / OpenSearch |
|---|---|---|---|---|
| Лицензия | AGPLv3 | Apache 2.0 | Apache 2.0 | Elastic License 2.0 (ELK), Apache 2.0 (OpenSearch) |
| Требования к ресурсам | Низкие: индексируются только метки | Средние | Низкие | Высокие: полнотекстовый индекс на весь объём |
| Стоимость хранения | Низкая: сжатые блоки в S3 | Низкая: колоночное сжатие | Низкая | Высокая |
| Полнотекстовый поиск | Ограниченный: фильтрация по подстроке в потоке, отобранном метками | Полный через SQL, включая аналитические запросы | Есть, без обязательных меток | Полный, с релевантностью |
| Язык запросов | LogQL, синтаксис близок к PromQL | SQL | LogsQL | Query DSL |
| Единый интерфейс с метриками и трейсами | Да, Grafana для всех трёх видов данных | Нет, нужен отдельный интерфейс или плагин | Через Grafana, менее зрело | Нет, свои дашборды |
| Управляемый сервис в Yandex Cloud | Нет, самостоятельное развёртывание | Да | Нет | Да (OpenSearch) |
| Разграничение доступа по ролям | Через Grafana | Средствами СУБД, гибко | Ограниченно | В ELK платно, в OpenSearch включено |
| Зрелость и практика в командах | Высокая | Высокая, но чаще как аналитическая СУБД | Низкая, проект молодой | Высокая |
| Порог входа для команды | Низкий при использовании Grafana | Средний: нужна схема таблиц и знание SQL | Средний | Средний |

Выбор: **Grafana Loki**.

### Обоснование

| Довод | Пояснение |
|---|---|
| Один стек наблюдаемости | Метрики (Task2), трейсы (Task3) и логи в одном интерфейсе Grafana. По алерту из метрик открываются логи того же сервиса за тот же интервал и трейс того же заказа. В компании один DevOps-инженер: три отдельных интерфейса он не обслужит |
| Дешёвое хранение | Индексируются только метки, тела записей лежат сжатыми в S3: стоимость гигабайта там ниже, чем на дисках инстансов. При линейном росте заказов объём логов растёт, и стоимость хранения становится определяющей |
| Достаточность поиска | Основной сценарий поддержки известен: найти логи по `order_id` за интервал. Это фильтрация по метке плюс поиск подстроки в отобранном потоке, а не полнотекстовый поиск по всему объёму |
| Связь с трейсингом | Метка `trace_id` в логах позволяет перейти из трейса в логи и обратно без ручного сопоставления |

### Почему не остальные

| Вариант | Причина отказа |
|---|---|
| ClickHouse | Сильная сторона - аналитические запросы и колоночное сжатие однотипных записей. Для логов это менее важно: записи разнородны, а основной сценарий - поиск по `order_id`, а не агрегация. При этом ClickHouse уже выбран как хранилище спанов в Task3, где сжатие даёт основной выигрыш. Остаётся кандидатом, если понадобится аналитика по логам за месяцы: тогда тот же инстанс переиспользуется |
| VictoriaLogs | По характеристикам подходит: экономно по ресурсам, поиск без обязательных меток. Отклонён из-за зрелости: проект молодой, практики в командах мало, а единственному DevOps-инженеру нужен инструмент с предсказуемым поведением и документацией |
| ELK, OpenSearch | Полнотекстовый поиск с релевантностью и зрелая экосистема, но требования к ресурсам и стоимость хранения выше остальных: индексируется весь объём, а не только метки. Полнотекстовый поиск по всему массиву в нашем сценарии не нужен. У ELK дополнительно ограничения лицензии Elastic License 2.0 и платное разграничение доступа по ролям, что для логов с идентификаторами клиентов обязательно |

### Управление жизненным циклом данных

Независимо от хранилища срок хранения задаётся политикой, а не удалением
отдельных записей: точечное удаление помечает записи, но не освобождает место до
слияния сегментов. Удаляются целые блоки или разделы данных.

| Этап | Реализация в Loki | Аналог в ELK |
|---|---|---|
| Создание | Поток определяется набором меток, отдельная настройка на каждый поток не нужна | Индекс по шаблону с заданным числом шардов и маппингом |
| Смена активного блока | По достижении размера или интервала блок закрывается и выгружается в объектное хранилище | Ролловер индекса по `max_age`, `max_size`, `max_docs` |
| Хранение | Свежие данные на быстрых дисках, старые в S3 | Перемещение индекса на более дешёвый уровень хранения |
| Удаление | Блоки старше срока удаляются политикой хранения | Удаление индекса политикой жизненного цикла |

Удаление по сроку нужно не только для экономии места: логи содержат
идентификаторы клиентов, и хранение дольше необходимого противоречит требованиям
к обработке персональных данных.

### Ограничение выбора

Loki плохо подходит для поиска по произвольному тексту без меток: запрос "найти все записи со словом timeout за месяц" сканирует блоки и выполняется медленно. Поэтому обязательны метки `service`, `environment`, `level`, `order_id` - они сужают выборку до начала поиска. Если появится потребность в аналитике по логам за длительный период, для этой задачи добавляется ClickHouse как отдельное хранилище, а Loki остаётся для оперативного разбора.
